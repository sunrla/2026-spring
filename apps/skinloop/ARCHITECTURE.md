# SkinLoop Architecture

SkinLoop is a local-first MVP built with Next.js App Router, TypeScript, Tailwind CSS, and browser localStorage.

## MVP Structure

The app is intentionally simple for a school final project:

- Frontend-only Next.js app
- No backend server
- No authentication
- No external APIs
- No real AI API
- Local mock data and local rules
- Browser localStorage persistence

This makes the project easy to run, demo, and grade while still showing a complete product loop.

## Major Routes

| Route | Purpose |
| --- | --- |
| `/` | Landing page, positioning, safety copy, demo data controls, presentation flow guide |
| `/survey` | Skin survey onboarding |
| `/products` | Product registration, catalog autofill, ingredient parsing, tag explanations |
| `/analysis` | Routine risk analysis from profile, products, tags, and logs |
| `/recommendation` | Local rule-based routine recommendation v1 |
| `/logs` | Weekly skin log entry |
| `/dashboard` | Progress dashboard using logs and products |
| `/admin` | Brand/admin B2B2C insight dashboard |

## localStorage Keys

SkinLoop stores only local MVP data in these keys:

- `skinloop.profile`
- `skinloop.products`
- `skinloop.weeklyLogs`

The demo reset control clears only these keys, not the whole browser storage.

## Key Data Models

### `SkinProfile`

Stores the survey result:

- dryness
- oiliness
- sensitivity
- redness
- breakouts
- mainGoal
- updatedAt

### `Product`

Stores current skincare products:

- id
- name
- brand
- category
- ingredientText
- frequency
- createdAt
- optional dataSource
- optional verificationStatus
- optional catalogProductId

### `WeeklyLog`

Stores routine observation logs:

- drynessScore
- oilinessScore
- rednessScore
- irritationScore
- breakoutCount
- sleepHours
- stressScore
- memo
- createdAt

### `IngredientRule`

Defines local mock ingredient tagging:

- tag
- Korean label
- short explanation
- routine meaning
- caution level
- evidence status
- source label
- disclaimer
- keyword list

### `RoutineRecommendation`

Generated by the local recommendation engine:

- dataCompletenessScore
- basisSummary
- morningRoutine
- eveningRoutine
- avoidList
- observationPlan
- reasonSummary
- safetyNote
- generatedAt

## Ingredient Rule And Tagging Overview

Ingredient text is entered as comma-separated text.

Example:

```text
Water, Glycerin, Fragrance, Limonene, Phenoxyethanol
```

The parser:

1. Splits the text by commas.
2. Trims each ingredient name.
3. Checks each ingredient against local keyword rules.
4. Returns parsed ingredients and detected tags.
5. Builds explanation cards showing matched ingredients per tag.

Example tags:

- `moisturizing`
- `fragrance-related`
- `preservative`
- `exfoliating-acid`
- `sunscreen`
- `potential-irritation-caution`

The rules are MVP demo rules, not verified official product data.

## Recommendation Engine Overview

`lib/recommendation.ts` generates a structured routine recommendation from:

- saved skin profile
- registered products
- detected ingredient tags
- weekly logs

The engine uses simple local rules:

- If dryness is high, emphasize consistent moisturizing/barrier-support observation.
- If oiliness is high, suggest lighter layering and controlled changes.
- If sensitivity or irritation logs are high, suggest slower product changes.
- If exfoliating acid tags are detected, suggest observing frequency and avoiding many changes at once.
- If fragrance-related tags and sensitivity signals appear together, suggest careful observation.
- If no sunscreen signal exists, suggest checking morning routine coverage.
- If data is missing, lower the data completeness score and explain the limitation.

The recommendation is local rule-based MVP guidance. It is not medical advice.

## Demo Data Flow

`seedDemoData()` writes:

- one `SkinProfile`
- three `Product` entries
- four `WeeklyLog` entries

This supports a predictable final presentation:

1. Seed demo data from the landing page or header.
2. Visit survey, products, analysis, recommendation, dashboard, and admin pages.
3. Reset local data when needed.

`clearDemoData()` removes only:

- `skinloop.profile`
- `skinloop.products`
- `skinloop.weeklyLogs`

## Why A Real LLM/API Is Not Connected Yet

The MVP avoids real AI and external APIs on purpose:

- School presentation stability
- No API keys required
- No network dependency
- Easier grading and local execution
- Lower privacy risk
- Safer wording control

The current recommendation page is built as a local rule-based version first. This proves the product flow before adding AI.

## Future Backend/API Path

A future production version could add:

- Backend API routes
- Database tables for users, products, logs, and recommendations
- Consent and privacy management
- Account-based sync
- Admin aggregation over anonymized data
- Evidence references for ingredient/routine rules
- Safe LLM recommendation layer with prompt guardrails
- Brand dashboard permissions
- Product-page widget integration

Before adding AI or brand analytics, the service would need clear consent, deletion, retention, and privacy policy design.

## Safety Positioning

SkinLoop should keep using language such as:

- 루틴 관찰
- 참고 정보
- 가능성 기반
- 제품 제안 보조
- 의학적 진단이나 치료를 제공하지 않습니다

The app should not claim that it diagnoses, treats, cures, prevents disease, or confirms exact product suitability.
